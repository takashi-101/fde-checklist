# フルリモートFDEジョブエイド（閉域ローカルLLM導入編）

## 概要（30秒で読めます）

- **問い**：外部の支援者が現場のネットワークに直接入れない閉域環境の案件で、閉域ローカルLLMの導入をどう進め、どう確かめるか。生成AIは、約款型クラウドAI・専用環境・ローカルLLMのどこに置くのが妥当か。
- **方法**：現場に入れない前提での確認手順を、6フェーズ・24項目のジョブエイド（チェックリスト）にまとめました。内容は [local-llm-record](https://github.com/takashi357/local-llm-record) の実測記録（機材構成の同等性の検証、出力と原典の照合、非送信の証跡）に基づいています。あわせて、デジタル庁 DS-920「生成AIの調達・利活用に係るガイドライン」（2025年5月）の公開基準に沿って配置を判定するツールを作りました。
- **結果**：チェックリスト（jobaid.html）は単一のHTMLファイルで、ブラウザで開くだけで使えます。外部リソースの読み込みや外部への送信はなく、オフラインで動きます。配置判定（cloud-or-local.html）も単一HTMLのツールで、データの中身・契約条件・実行環境の3問に答えると、妥当な配置を根拠とあわせて示します。
- **私の役割**：local-llm-record の測定記録を土台に、このチェックリストと判定ツールを作成しました。

もとは local-llm-record の `fde/` フォルダにあったものを、このリポジトリに移しました。

FDE（Forward Deployed Engineer）は、顧客の現場に入り、要件のヒアリングから導入・定着までを一貫して担うエンジニア職です。

FDEは「現場に入る」ことが前提の職種ですが、閉域環境（インターネットに接続しない環境）の案件では、外部の支援者が現場のネットワークに直接入れないことがよくあります。このリポジトリのジョブエイド（作業時に手元で参照するチェックリスト）は、**現場に入れない前提で閉域ローカルLLMの導入を進める**ための確認手順を、6フェーズ・24項目にまとめたものです。内容は、[local-llm-record](https://github.com/takashi357/local-llm-record) の実測記録（機材構成の同等性の検証、出力と原典の照合、非送信の証跡）に基づいています。

## 使い方

[jobaid.html](jobaid.html) をブラウザで開くだけで使えます。

- 単一のHTMLファイルです。外部リソースの読み込みや外部への送信はなく、オフラインで動きます
- チェック状態とメモは、そのブラウザのlocalStorageにのみ保存されます
- 「印刷」ボタンからPDFにして、案件の記録として残せます

## フェーズ構成

0. 案件開始前 — 契約・条項（生成AIの利用可否に関する条項、データ区分の確定）
1. リモートヒアリング — 環境の同等性（メモリ割り当て、モデルサイズ、閉域の条件）
2. 手元での同等環境の検証（文書の同一性確認、方式の実測による選定）
3. 導入 — 導入先の担当者が実行する前提の手順書
4. 検収 — 出力の照合と、外部に送信していないことの証明
5. 引き渡し・運用

## 生成AI配置判定エイド（cloud-or-local.html）

[cloud-or-local.html](cloud-or-local.html) は、扱うデータの中身・契約条件・実行環境の3問に答えると、「約款型クラウドAI／専用環境（ガバメントクラウド・オンプレミス）／ローカルLLM」のどれが妥当かを、根拠とあわせて示す単一HTMLのツールです。

判定は、デジタル庁 DS-920「生成AIの調達・利活用に係るガイドライン」（2025年5月）の公開基準に基づいています。ガバメントクラウドの対象クラウド事業者（AWS・Microsoft Azure・Google Cloud・Oracle Cloud・さくらのクラウド）を前提に、クラウドを最初から除外せず、「クラウドで良い場合」と「ローカルしかない場合」を分けて示します。機密性区分の番号の付け方は組織によって逆になる場合があるため、区分の名称ではなく、データの中身で選ぶ形にしています。

## チェックリストの構成について

本チェックリストと関連ツールは、導入支援の工程（業務理解・課題特定 → 設計 → 実装 → 定着 → 成果）に沿って整理しています。あわせて、第三者が同じ手順で結果を確かめられること（再現性）を重視し、各工程の成果物を検証できる形で残すようにしています。

表の rag.py・model-check/・genai/・check.py・evidence.py は [local-llm-record](https://github.com/takashi357/local-llm-record) にあります。

| 工程 | 対応するツール・記録 |
|---|---|
| 1. 業務理解・課題特定 | ジョブエイドのフェーズ0〜1（契約条項・データ区分・環境の同等性のヒアリング） |
| 2. 設計 | 配置判定（cloud-or-local.html）、kの値を変えた実測による方式選定（rag.py）、モデルの受け入れ検査（model-check/） |
| 3. 実装 | WSLのメモリ割り当て7.6GBで動く構成（genai/）、導入先の担当者が実行する前提の手順書（フェーズ3） |
| 4. 定着（教育・指導） | 技術職以外の利用者向けのブラウザUI、運用の引き渡し（フェーズ5） |
| 5. 成果（KPI） | 原典との照合による検収（check.py）、非送信の証跡（evidence.py）、実測値の記録 |
| 再現性 | コード・手順・実測値の公開、SHA-256による文書・モデルの同一性確認、ハッシュチェーンの再検証（誰でも verify を再実行できる） |
